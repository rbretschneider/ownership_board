# Registry persistence and management

Build hosts have independent identity, lifecycle, and scheduling metadata.
Migration 0013 adds their registry and pairing-code metadata without changing
existing runner settings. Rolling it back removes these two new tables.

Ed25519 keys remain unique after revocation. Human management writes update
only administrative columns, preserving host report fields for future agent
updates. SQLite write transactions serialize lifecycle actions; approval also
uses a conditional pending-state update. Revocation is terminal and repeatable
without rewriting its timestamp.

The management API checks human authentication before Origin checks or bearer
write limits. Authorized browser writes still require the existing Origin
validation, and authorized agent writes elsewhere still use their limiter.
Application services repeat the human check before accessing storage.

Codes use cryptographic randomness and hash-only persistence. The in-memory
issuance result wraps plaintext in the existing redacting secret type; only
the HTTP issuance DTO reveals it. Code consumption is not yet exposed.

Successful mutations log safe administrative metadata after commit. Logging
uses the existing best-effort logger and is not a durable transactional audit
outbox. No-op edits and repeated revocation do not produce mutation logs.
